# 第 12 章 RAG 评测与实验设计

> 返回 [全书目录](../00-全书导读与目录.md)。上一篇：[11-检索进阶与GraphRAG](11-检索进阶与GraphRAG.md)；下一篇：[13-Agent工程实践](../第四篇-Agent工程/13-Agent工程实践.md)。

> [!abstract] 本章解决什么问题
> 没有评测的 RAG 调优，本质是「凭感觉改参数」——今天好了明天坏，永远说不清为什么。
> 本章给出可落地的评测体系：指标、黄金集、实验设计、统计判断、上线门禁。

---

## 12.1 评测的四层结构

| 层 | 评什么 | 指标 | 谁来评 |
| --- | --- | --- | --- |
| 检索层 | 找得对不对 | Recall@K、Precision@K、MRR | 程序（有黄金块标注） |
| 生成层 | 答得忠不忠 | Faithfulness、Answer Relevancy | 模型判分 + 人工抽检 |
| 业务层 | 有没有用 | 一次解决率、转人工率、满意度 | 线上数据 |
| 系统层 | 快不快、贵不贵 | P95 延迟、单次成本、错误率 | 监控 |

> [!important] 原则
> **先有检索层指标，再谈生成层。** 检索错了，生成再漂亮也是错的。很多团队只测「答案像不像」，结果永远定位不到问题。

---

## 12.2 黄金评测集怎么建

### 三条硬标准

1. **来自真实问题**：客服记录、工单、销售问答，不要自己编；
2. **标注三件套**：问题 + 标准答案 + 应命中的文档块 ID；
3. **覆盖四类**：高频、长尾、易错、越界（该拒答的）。

### 规模与结构

| 阶段 | 规模 | 构成 |
| --- | --- | --- |
| 起步 | 100 条 | 高频 60 + 长尾 25 + 易错 10 + 越界 5 |
| 稳定 | 300–500 条 | 按真实分布分层 |
| 持续 | 每次 Bad Case 回灌 | 线上问题 → 评测集 |

### 标注规范示例

```json
{
  "id": "q_0042",
  "question": "出差住宿标准是多少？",
  "answer": "一线城市 600 元/晚，其他城市 450 元/晚（依据《差旅管理办法》第 12 条）。",
  "gold_chunks": ["doc_017#c3", "doc_017#c4"],
  "type": "高频",
  "difficulty": "easy"
}
```

## 12.3 四个核心指标的计算逻辑

| 指标 | 计算思路 | 低说明什么 | 目标 |
| --- | --- | --- | --- |
| Context Recall | 黄金块中被召回的比例 | 分块/Embedding/查询改写有问题 | ≥ 0.85 |
| Context Precision | 召回块中相关块的比例与排序质量 | 噪声多、缺重排 | ≥ 0.75 |
| Faithfulness | 回答中的陈述有多少能被资料支持 | 幻觉、提示词太松 | ≥ 0.90 |
| Answer Relevancy | 回答与问题的语义相关度 | 跑题、提示词含糊 | ≥ 0.85 |

事实依据：RAGAS（Es 等，2023）提出用 LLM 作为评判者自动计算上述指标；工程上通常「模型判分 + 人工抽检 5%」结合使用，避免单一判分器的偏差。

## 12.4 实验设计：一次只改一个变量

### 反例（常见错误）

```text
这周改了：分块 300→500、加了重排、换了 Embedding、改了提示词
结果：指标从 0.72 涨到 0.81
问题：不知道是哪个改动的功劳，也不知道有没有互相抵消
```

### 正确做法

| 步骤 | 动作 |
| --- | --- |
| 1 | 固定基线：记录当前全部参数与指标 |
| 2 | 只改一个变量（如分块 300→500） |
| 3 | 跑黄金集，重复 3 次取均值（temperature=0） |
| 4 | 对比指标，判断是否显著 |
| 5 | 记录结论，进入下一个变量 |

### 判断「显著」的土办法

| 指标变化 | 判断 |
| --- | --- |
| < 1% | 噪声范围，不算提升 |
| 1%–3% | 需重复验证，可能不稳定 |
| > 3% | 可信提升（结合样本量看） |
| 某指标升、另一指标降 | 权衡，看业务更在意哪个 |

> [!warning] 别被单次结果骗
> LLM 判分有随机性，单次跑分差异 2–3% 很正常。**要么跑多次取均值，要么把样本量加大。**

## 12.5 调参优先级与预期收益

| 顺序 | 动作 | 预期收益 | 成本 |
| --- | --- | --- | --- |
| 1 | 修数据质量（解析/去重/版本） | 高 | 人力 |
| 2 | 调分块（大小/重叠/结构切分） | 高 | 低 |
| 3 | 加查询改写（扩写/消解） | 中高 | 低 |
| 4 | 加混合检索 + RRF | 中高 | 中 |
| 5 | 加重排 | 中 | 中（延迟 +150ms） |
| 6 | 调提示词与拒答 | 中 | 低 |
| 7 | 换更大模型 | 低-中 | 高 |
| 8 | 微调 | 低（对知识类） | 很高 |

> [!tip] 经验之谈
> 大多数「效果不好」的项目，问题出在 1–3 步。**先花两天修数据与分块，往往比换模型提升更大。**

## 12.6 上线门禁（写进运维方案）

| 门禁项 | 阈值 |
| --- | --- |
| Context Recall | ≥ 0.85 |
| Faithfulness | ≥ 0.90 |
| P95 延迟 | ≤ 3 秒 |
| 越权访问 | 0 次 |
| 相比上一版本 | 任一核心指标下降 > 3% 则禁止发布 |

```text
发布流程：
跑黄金集 → 生成报告 → 与基线对比 → 通过门禁 → 灰度 5% → 观察 24h → 放量
                                     ↓ 不通过
                                  打回优化
```

## 12.7 线上评测：比离线更重要

| 手段 | 做法 | 价值 |
| --- | --- | --- |
| 点赞/点踩 | 每次回答带反馈按钮 | 最真实的信号 |
| 转人工率 | 统计转人工占比 | 直接反映「没解决」 |
| 抽样人工评估 | 每周抽 50 条 | 发现模型判分盲区 |
| Bad Case 归因 | 分类统计 | 指导优化方向 |
| A/B 实验 | 新旧版本分流 | 验证真实收益 |

> [!important] 一句话
> 离线评测保证「不发版退步」，线上评测决定「下一步往哪优化」。

## 12.8 LLM 做裁判：能用，但必须知道它什么时候不可靠

用大模型自动打分（LLM-as-Judge）是规模化评测的唯一现实选择，但它有三个稳定的偏置：

| 偏置 | 表现 | 应对 |
| --- | --- | --- |
| **位置偏置** | 两个答案对比时，偏爱排在前面/后面的那个 | 交换顺序测两次，取一致结果 |
| **长度偏置** | 偏爱更长、更详细的答案 | 显式提示「不要因为长就给高分」 |
| **自我偏好** | 偏爱与自己风格相似的答案 | 用不同家族模型做裁判，或加人工抽检 |

**可行性与成本**：

```text
人工评测：100 题 × 3 分钟/题 = 5 小时/轮
LLM 评测：100 题 × 1 次调用 ≈ 5 分钟/轮，成本约 1–3 元
```

**关键指标：与人工的一致率**。做法：

| 步骤 | 做法 |
| --- | --- |
| 1 | 抽 50 题，人工打分（0/1/2） |
| 2 | 同一批用 LLM 打分 |
| 3 | 算一致率（完全相同 / 相差 1 分以内分别统计） |
| 4 | 一致率 ≥85% 才可用来替代人工做日常回归 |

> [!important] 一条纪律
> **LLM 裁判只能用于「相对比较」和「回归检测」，不能用于「对外承诺的指标」。**
> 客户验收的指标必须由人工（或明确规则）判定。把 LLM 打分写进验收条款，等于给项目埋雷。

## 12.9 一份完整的评测报告模板

评测报告不是「跑完给个数」，要能让别人复现、能支撑决策。

```markdown
## 一、评测目标
本次评测回答的问题：分块从 500 改到 300，是否值得？（单变量）

## 二、数据集
- 黄金集 v3：100 题（简单 30 / 多段 20 / 精确 20 / 表格 10 / 术语 10 / 应拒答 10）
- 来源：真实工单抽样 + 业务专家确认
- 标注人：业务专家 2 人，交叉校验一致率 92%

## 三、被测配置
| 项 | 基线 | 实验组 |
| 分块 | 500 字 / 重叠 15% | 300 字 / 重叠 15% |
| 其余 | 完全相同 | 完全相同 |

## 四、结果
| 指标 | 基线 | 实验组 | 变化 | 是否显著 |
| Context Recall | 0.83 | 0.79 | −0.04 | 是（n=100，差值>0.03） |
| Context Precision | 0.68 | 0.71 | +0.03 | 边界 |
| Faithfulness | 0.91 | 0.91 | 0 | 否 |

## 五、结论与建议
分块变小后 Precision 微升但 Recall 下降，且不达门禁（≥0.85）。
结论：维持 500 字；下一步试「父子块（子 300 / 父 1200）」。

## 六、附录
失败样例 8 条（含问题、命中块、模型答案、期望答案）
```

> [!tip] 第六节「失败样例」是整份报告最有用的部分
> 数字告诉你「差多少」，样例告诉你「为什么差」。**没有样例的评测报告，下一个人没法接着改。**

## 12.10 评测集的维护：它会腐烂

黄金集不是建一次用三年。三个必须做的维护动作：

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| **数据泄漏** | 指标虚高，上线后暴跌 | 评测题不进训练/微调数据；题库定期换新 |
| **题目过时** | 业务变了，题还是老的 | 每季度淘汰 10%、补 10% |
| **难度漂移** | 全都能答对，失去区分度 | 加入新的 hard case（从线上 bad case 抽） |

**维护节奏**：

```text
每月：从线上点踩 Top20 中抽 5 条，标注后加入评测集
每季：淘汰「所有模型都能答对」的题 10%，补入新场景题 10%
每年：整体复核一遍，检查题目与现行业务是否一致
```

> [!warning] 一个隐蔽的坑
> **微调时把评测集混进训练数据**，是最常见的自欺欺人。
> 表现是：离线指标 0.95，上线后 0.6。做微调前，先把评测集「隔离」到一个独立目录，并在训练脚本里显式排除。

## 12.11 本章考点速记

> [!success]- 必背 7 条（点击展开自测）
> 1. 评测四层：检索、生成、业务、系统。
> 2. 黄金集三件套：问题 + 标准答案 + 应命中块；四类覆盖：高频、长尾、易错、越界。
> 3. 四指标：Recall ≥0.85、Precision ≥0.75、Faithfulness ≥0.90、Relevancy ≥0.85。
> 4. 实验纪律：一次只改一个变量，跑 3 次取均值。
> 5. 变化 <1% 视为噪声，>3% 才算可信提升。
> 6. 调参优先级：数据 → 分块 → 查询 → 混合检索 → 重排 → 提示词 → 模型 → 微调。
> 7. 上线门禁：核心指标不降 3%，灰度 5% 观察 24 小时。
