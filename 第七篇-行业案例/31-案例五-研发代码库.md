## 31.1 客户与现状：新人被「找不到」拖住

某软件公司，40 个代码仓库、2 万份技术文档、大量历史工单。研发 300 人，年离职率 18%。

| 现状数据 | 数值 | 问题 |
| --- | --- | --- |
| 代码仓库 | 40 个（含 8 个历史遗留） | 同一功能在多个仓库有不同实现 |
| 技术文档 | 约 2 万份 | 大部分过时，无版本标注 |
| 历史工单 | 约 12 万条 | 大量重复问题，含解决方案 |
| 新人查一个问题 | 平均 60 分钟 | 问人、搜 Confluence、翻代码 |
| 新人上手周期 | 6 周 | 导师被反复打断 |
| 导师日均被打断 | 约 9 次 | 每次 10–20 分钟 |

**立项触发点**：一个季度内两位核心开发离职，留下的模块无人能维护；新人问「这个报错什么意思」，答案散落在三年前的工单里。

> [!important] 研发知识库的核心矛盾
> **代码是「最新即正确」，文档是「写了就过时」。**
> 所以这类项目最重要的不是「答得好」，是**「答的是当前分支的最新代码」**——一个引用已废弃分支的答案，比不答更糟。

---

## 31.2 需求澄清：三类问题，三种解法

我们让客户提供一周内新人实际问的 200 个问题，聚类后只有三类：

| 类型 | 占比 | 例子 | 解法 |
| --- | --- | --- | --- |
| **接口怎么用** | 42% | 「这个 SDK 的 init 要传什么」 | 代码 + 注释 + 文档混合检索 |
| **报错什么原因** | 35% | 「`NullPointerException` at OrderService:142」 | 工单库检索（历史解决方案） |
| **业务规则是什么** | 23% | 「订单超时多久自动取消」 | 文档检索 + 代码常量定位 |

> [!tip] 这个分类直接决定了架构
> 如果只做「文档 RAG」，只能解决 23%；只做「代码 RAG」，只能解决 42%。
> **必须先分类再路由**——这就是 16.2 里 Router 拓扑的价值。很多项目失败在「一个索引打天下」。

## 31.3 约束清单

| 约束 | 具体 | 影响 |
| --- | --- | --- |
| 代码 | 需按函数/类切分，保留上下文 | **AST 感知切分**，不用字数切 |
| 权限 | 不同项目组代码隔离 | 仓库级 + 分支级权限 |
| 更新 | 代码天天变（日均 80 次 commit） | 增量索引（按 commit 触发） |
| 查询 | 报错信息、函数名是强特征 | BM25 权重提高，精确匹配优先 |
| 输出 | 需要可直接复制的代码片段 | 格式化输出 + 语法高亮 + 文件:行号 |
| 时效 | 分支有生命周期 | 只索引活跃分支，废弃分支排除 |

---

## 31.4 被否决的三个方案

| 方案 | 看起来的优点 | 否决理由 |
| --- | --- | --- |
| A 只做文档 RAG | 简单、文档干净 | 只能解决 23% 的问题，用户不会用 |
| B 用 IDE 插件（代码补全思路） | 贴合开发者习惯 | 客户要的是「问答」，不是补全；且 40 个仓库的插件部署成本高 |
| C 全量重建索引（每小时一次） | 实现简单、无需处理增量 | 全量重建 4 小时，**每小时一次等于永远在重建** |

## 31.5 总体架构

| 层 | 设计 | 关键参数 |
| --- | --- | --- |
| 切分（代码） | **AST 按函数/类切**，附带文件路径、模块名、签名、docstring | 单块 ≤800 Token，超长函数按逻辑块再切 |
| 切分（文档） | 按标题层级切 | 400 字，重叠 15% |
| 切分（工单） | 一单一文档，含标题、报错、解决方案 | 报错信息单独成字段 |
| 元数据 | 仓库、分支、文件路径、行号、语言、最后提交时间 | **分支与提交时间是硬过滤** |
| 检索 | 三路召回：BM25（函数名/报错码，权重 1.5×）+ 向量 + 符号索引 | 融合用 RRF（k=60） |
| 重排 | 交叉编码器，输入「问题 + 代码块 + 文件路径」 | 召回 50 → 重排 Top5 |
| 生成 | 输出「原因 + 示例代码 + 引用 文件路径:行号」 | 代码必须可复制 |
| 更新 | 监听 Git 事件，按 commit 增量重建受影响块 | 延迟 <5 分钟 |

## 31.6 代码切分：这个案例的技术核心

按字数切代码会发生什么？举个真实例子：

```python
# 原始函数（被按 300 字硬切后）
def calculate_discount(order, user):
    if user.level == "VIP":
        rate = 0.9
    # ← 切点在这里，后面被切到下一个块
    elif user.coupon:
        rate = 0.95
    else:
        rate = 1.0
    return order.amount * rate
```

模型拿到前半块，会「补全」出一个 `return order.amount`——**看起来完全合理，但是错的**。这类错误最难发现，因为它语法正确、逻辑自洽。

**AST 切分的四条规则**：

| 规则 | 说明 |
| --- | --- |
| 以函数/类为最小单元 | 不跨越 def/class 边界切 |
| 附带上下文头 | 文件路径、模块、类名、函数签名、docstring |
| 超长函数按逻辑块切 | 保留 `def` 行 + 参数，避免「无头函数」 |
| 保留 import 区 | 单独成块，因为「这个类从哪来」是高频问题 |

> [!important] 一条判断
> **结构化内容（代码、表格、条款）必须用结构感知的切分器。**
> 通用分块器在这类场景一定翻车——这不是调参能解决的，是方法错了。

## 31.7 增量索引：日均 80 次 commit 的应对

全量重建 4 小时，日均 80 次 commit，显然不能每次都重建。

```text
Git webhook → 解析 commit diff
  ├─ 找出变更文件
  ├─ 对每个文件重新做 AST 切分
  ├─ 对比旧块集合：新增 / 修改 / 删除
  ├─ 只对「新增 + 修改」的块重新 Embedding
  ├─ 删除已消失的块（软删除，保留 7 天可回滚）
  └─ 更新索引版本号
```

| 指标 | 全量重建 | 增量更新 |
| --- | --- | --- |
| 耗时 | 4 小时 | **<5 分钟** |
| 计算成本 | 100% | 约 3% |
| 数据一致性风险 | 低 | 中（需处理删除与重命名） |
| 适用 | 首次建库、模型换代 | 日常更新 |

> [!warning] 增量更新的三个坑
> ① **文件重命名**被当成「删除 + 新增」，导致同一内容两份块 → 用内容 hash 去重。
> ② **删除未同步**，检索到已删除的代码 → 必须做软删除 + 定期对账。
> ③ **Embedding 模型换代**时不能增量，必须全量重建（向量空间变了，见 04.6）。

## 31.8 关键调优：四个真实问题

| 问题 | 现象 | 解法 | 效果 |
| --- | --- | --- | --- |
| 按字数切代码 | 函数被劈成两半，答案语法错误 | AST 切分 + 上下文头 | 语法错误率 18% → 2% |
| 忽略分支 | 检索到已废弃分支的代码 | 只索引活跃分支 + 分支元数据过滤 | 答非所问 12% → 1% |
| 不做增量 | 每次全量重建 4 小时 | Git 事件驱动增量 | 延迟 4 h → 5 min |
| 符号检索弱 | 搜「OrderService.cancel」找不到 | 建符号索引（类名/方法名/常量名） | 精确匹配召回 +31 pt |

**符号索引是什么**：把代码里的类名、方法名、常量名、配置键抽出来单独建一份索引，与向量索引并行。查询里出现标识符时，优先走符号索引。

> [!tip] 研发场景的通用规律
> **开发者的问题里，标识符（函数名、报错码、配置项）出现的频率远高于自然语言。**
> 所以这类系统的 BM25 / 符号索引权重应该高于向量检索——这和客服场景正好相反。

## 31.9 指标结果

| 指标 | 上线前 | 上线后 | 测量方法 |
| --- | --- | --- | --- |
| 平均检索耗时 | 60 分钟 | 5 分钟 | 抽样 100 次实测 |
| 新人上手周期 | 6 周 | 3 周 | HR 统计「首次独立提交」时间 |
| 引用准确率（文件:行号） | — | 93% | 抽检 200 条，核对行号是否真的包含该逻辑 |
| 索引更新延迟 | 4 小时（全量） | <5 分钟 | 监控 |
| 导师日均被打断 | 9 次 | 4 次 | 抽样统计 |
| 代码片段可编译率 | — | 88% | 抽 50 条，实际粘贴编译 |

> [!warning] 「引用准确率 93%」这个数要小心
> 行号会随代码变动而漂移。我们的做法是**引用「文件 + 函数名 + 附近代码片段」，行号只作辅助**。
> 只给行号的引用，一周后就会失效——这是研发场景特有的坑。

## 31.11 踩过的三个坑

| # | 坑 | 后果 | 改法 |
| --- | --- | --- | --- |
| 1 | 按字数切代码 | 函数被切成两半，答案全是语法错误 | 必须 AST 切分 |
| 2 | 忽略分支 | 检索到已废弃分支的代码，答非所问 | 加分支过滤 + 只索引活跃分支 |
| 3 | 不做增量 | 每次全量重建 4 小时 | 增量后 5 分钟内完成 |

---

## 31.12 如果重来，会怎么改

| 改动 | 理由 |
| --- | --- |
| 先做「符号索引」再做向量索引 | 标识符精确匹配是研发场景的主要召回来源 |
| 引用格式定为「文件+函数名+片段」，行号只作辅助 | 行号漂移会让引用快速失效 |
| 工单库和代码库分开建索引，用 Router 分流 | 混在一起会让「报错类」问题被代码块淹没 |
| 索引更新做成可回滚 | 增量出错时能快速回到上一个版本 |

---

## 31.13 可复用的判断

> [!important] 三条可以带走
> ① 结构化内容（代码、表格、条款）**必须用结构感知的切分器**，通用分块器在这类场景一定翻车。
> ② **标识符密集的场景，BM25/符号索引权重应高于向量**——这与自然语言问答场景相反。
> ③ 引用要给「稳定的定位」（函数名、条款号），不要给「会漂移的定位」（行号、页码可以，但要配合其他信息）。

## 31.14 本章考点速记

> [!success]- 折叠背诵版
> **三类问题**：接口怎么用 42% / 报错什么原因 35% / 业务规则 23% → **必须 Router 分流**。
>
> **三个否决**：只做文档（23% 覆盖率）、IDE 插件（不是问答需求）、全量重建（4 小时）。
>
> **AST 切分四规则**：以函数/类为最小单元、附带上下文头、超长按逻辑块切、import 单独成块。
>
> **增量索引**：Git webhook → diff → 重切 → 块集合对比 → 只 Embedding 新增/修改 → 软删除。
> **三个坑**：重命名当新增、删除未同步、模型换代不能增量。
>
> **指标**：检索 60 min→5 min、上手 6 周→3 周、引用准确 93%、更新延迟 <5 min、可编译率 88%。
>
> **一句话**：结构感知切分；标识符权重高于语义。
