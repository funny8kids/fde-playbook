## 43.0 怎么用这份基准库

这份表解决一个具体问题：**客户问「准确率多少算合格」，你答不出数字时，能翻到一页给出可辩护的区间。**

三条使用规则：

| 规则 | 说明 |
| --- | --- |
| **它是「起点」，不是「标准」** | 所有数字是经验区间，必须用你自己的黄金集重新标定 |
| **先对齐定义，再比数字** | 「准确率」在不同团队含义不同，先确认计算口径（见 12.3） |
| **写进合同时取区间下沿** | 内部目标取上沿，对外承诺取下沿，中间是缓冲 |

> [!WARNING]
> **一个必须说清的事实**
>
> 没有任何行业标准规定「RAG 的 Context Recall 必须 ≥0.85」。这个数字来自实践共识，用于**内部判断「还差多少」**，不能作为验收依据的唯一条款。
> 验收条款必须写成「以双方确认的 100 题测试集为基准，指标 ≥ X」（见 22.6）。

## 43.1 RAG 检索与生成指标

| 指标 | 定义 | 经验区间（可用 / 良好 / 优秀） | 备注 |
| --- | --- | --- | --- |
| Context Recall | 相关文档被召回的比例 | 0.75 / 0.85 / 0.92 | 最重要，低了后面全废 |
| Context Precision | 召回内容中相关的比例 | 0.65 / 0.75 / 0.85 | 影响 Token 成本与干扰 |
| Faithfulness | 答案中陈述可由上下文支持的比例 | 0.85 / 0.90 / 0.95 | 低于 0.85 会明显出现编造 |
| Answer Relevancy | 答案与问题的相关程度 | 0.78 / 0.85 / 0.92 | 低于 0.78 常见「答非所问」 |
| 有答案率 | 有引用的回答 / 总提问 | 0.70 / 0.80 / 0.88 | 过高需怀疑编造 |
| 拒答恰当率 | 该拒的拒了 + 该答的答了 / 总数 | 0.80 / 0.88 / 0.94 | 比单纯「拒答率」更有意义 |
| 引用准确率 | 引用确实支持该句的比例 | 0.88 / 0.94 / 0.98 | 金融/医疗必须 ≥0.95 |
| 一次解决率 | 无需追问/转人工即解决 | 0.55 / 0.68 / 0.80 | 业务方最认这个数 |
| Top-5 命中率 | 正确答案在 Top5 内的比例 | 0.80 / 0.88 / 0.94 | 检索层调优的主要看板 |

## 43.2 Agent 指标

| 指标 | 定义 | 经验区间 | 备注 |
| --- | --- | --- | --- |
| 任务完成率 | 端到端达成目标的比例 | 0.60 / 0.75 / 0.88 | 按任务类型差异极大 |
| 工具调用正确率 | 选对工具且参数合法的比例 | 0.85 / 0.92 / 0.97 | 低于 0.85 先改工具描述 |
| 平均步数 | 完成任务的平均轮次 | 与任务相关，越少越好 | 突增=规划退化 |
| 越权/越界率 | 访问未授权资源或执行未授权动作 | **必须 0** | 非 0 即事故 |
| 循环卡死率 | 触发最大轮次上限的比例 | ≤0.02 | 超过说明状态机设计有问题 |
| 人工介入率 | 需人审/接管的比例 | 按风险分级设定 | L3 动作应 100% 介入 |
| 平均单任务成本 | 一次任务的 Token 成本 | 与单 Agent 比 ≤5× | 超过说明编排过重 |
| 轨迹合规率 | 执行路径符合预设流程的比例 | 0.90 / 0.95 / 0.98 | 审计场景必测 |

## 43.3 文档解析与数据质量

| 指标 | 定义 | 合格线 | 抽检方法 |
| --- | --- | --- | --- |
| 字符准确率 | 解析文本与原文字符一致率 | ≥0.98 | 随机 10 页人工比对 |
| 结构完整率 | 标题层级/章节保留比例 | ≥0.95 | 抽 20 份看目录层级 |
| 表格还原率 | 表格结构正确率 | ≥0.90 | 抽 20 个表格 |
| 扫描件 OCR 准确率 | 印刷体/手写体 | 0.97 / 0.85 | 分类抽检 |
| 重复率 | 重复内容占比 | ≤0.02 | hash 去重统计 |
| 元数据完整率 | 必填字段齐全的比例 | ≥0.98 | SQL 统计 |
| 敏感信息明文率 | 未脱敏敏感字段占比 | **0** | 抽 100 条扫描 |
| 分块有效率 | 未被切断语义单元的比例 | ≥0.95 | 抽 50 块人工看 |

## 43.4 性能与容量

| 指标 | 场景 | 经验目标 | 备注 |
| --- | --- | --- | --- |
| TTFT（首 Token） | 交互式问答 | ≤1.5 s | 决定「感觉快不快」 |
| P95 端到端 | 交互式问答 | ≤6 s | 承诺 SLA 用它 |
| P95 端到端 | 后台批处理 | ≤30 s | 可放宽 |
| P99 端到端 | 全部 | ≤2× P95 | 长尾控制 |
| 并发承载 | 内部系统 | 峰值 × 1.3 余量 | 见 24.1 |
| 单卡吞吐（7B INT4） | 24G 卡 | 800–1500 token/s（批量） | 与框架、批大小强相关 |
| GPU 利用率 | 生产 | 40–70% | 长期 <30% 说明配多了 |
| 可用性 | 生产 | 99.5%（内部）/ 99.9%（对外） | 决定运维投入 |
| 故障恢复时间 | 生产 | ≤30 min | 需有降级链 |

## 43.6 商务与交付

| 指标 | 经验值 | 说明 |
| --- | --- | --- |
| 毛利率（项目制） | 30–40% | 低于 25% 建议不接 |
| 毛利率（硬件占比高） | 10–20% | 硬件是透明段 |
| 年运维费占比 | 建设额的 15–25% | 混合模式的核心收入 |
| 回收期（客户侧） | 8–24 个月 | 超过 24 个月立项难 |
| POC 周期 | 4–8 周 | 超过 8 周几乎必烂尾 |
| POC 转商机率 | 40–60% | 低于 30% 说明筛选有问题 |
| 需求变更率 | 15–30% | 超过 40% 说明需求没做透 |
| 数据工程占实施比 | 30–45% | 最常被低估 |
| 项目超期率 | 30–50%（行业普遍） | 排期时按 1.3 系数留缓冲 |
| 验收一次通过率 | 60–80% | 低于 60% 说明验收标准没定清 |

## 43.7 运营指标

| 指标 | 健康区间 | 异常含义 |
| --- | --- | --- |
| 日活 / 覆盖人数 | 30–60% | 低于 20% 说明没融进流程 |
| 人均日提问次数 | 3–15 | 过低=不好用，过高=可能在替人干活 |
| 点踩率 | ≤15% | 上升=内容过时或检索退化 |
| 转人工率 | 与场景相关 | 上升=信任流失 |
| 追问率（同会话轮次） | 1.2–2.0 轮 | 高于 2.5 说明一次答不清 |
| 引用点击率 | 20–40% | 过低=引用是装饰 |
| 内容月更新率 | ≥5% | 低于 2% 说明知识在腐烂 |
| 过期内容占比 | ≤5% | 超过 10% 必然出现错误答案 |

## 43.8 指标设计的五条原则

| 原则 | 说明 | 反例 |
| --- | --- | --- |
| **可测** | 能用脚本或明确判定规则算出来 | 「用户体验好」 |
| **可归因** | 指标下降时能定位到哪一层 | 「整体准确率 80%」（哪层错？） |
| **有基线** | 有「改造前」的数才能说「提升了」 | 只报上线后的数 |
| **有样本量** | 说明测了多少题、谁判定 | 「测了一下，还行」 |
| **有门禁** | 低于多少不上线 | 指标只是「看着好看」 |

> [!TIP]
> **一份合格的验收指标长什么样**
>
> 「以双方确认的 100 题测试集为基准，由甲方业务专家判定：Context Recall ≥0.85、Faithfulness ≥0.90、引用准确率 ≥0.95、拒答恰当率 ≥0.85；任一项不达标则进入 15 个工作日整改，复测一次。」
> **五要素齐全：样本、判定人、四个指标、阈值、整改机制。** 这段话可以直接抄进合同。
