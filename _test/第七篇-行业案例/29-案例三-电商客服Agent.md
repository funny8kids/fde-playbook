# 第 29 章 案例三 电商客服 Agent

> 返回 [全书目录](../00-全书导读与目录.md)。上一篇：[28-案例二-金融合规问答](28-案例二-金融合规问答.md)；下一篇：[30-案例四-政务信创知识库](30-案例四-政务信创知识库.md)。

> [!NOTE]
> **本章解决什么问题**
>
> 大促咨询量翻 3 倍，机器人还要能查订单、改地址、发起退款——写操作怎么开才不出事？
>
> - 按风险分级开放写权限（只读 → 可回滚 → 人审）
> - 用幂等键与细分错误码防重复与瞎猜
> - 设计四阶段上线路径与量化门槛
>
> **产出**：一套带护栏的客服 Agent 与上线节奏　|　预计 15 分钟


## 29.1 客户与现状：一个被大促逼出来的项目

某电商平台，日咨询量 6 万次，客服 300 人。平日勉强扛得住，**大促期间咨询量翻 3 倍**，临时招人培训要 3 周，根本来不及。

| 现状数据 | 数值 | 问题 |
| --- | --- | --- |
| 日咨询量 | 6 万次（大促 18 万） | 峰值是平日的 3 倍 |
| 客服人力 | 300 人（大促临时加 150） | 临时人力培训周期 3 周 |
| 单次咨询成本 | 约 3.5 元 | 人力成本刚性 |
| 重复问题占比 | 约 68% | 「什么时候发货」「怎么退货」 |
| 平均首响 | 28 秒 | 大促期间涨到 2 分钟以上 |
| 售后满意度 | 82% | 大促期间跌到 71% |

**客户最初的需求**是「做个问答机器人」。但聊到第三次，真正的诉求浮出来了：**他们希望机器人能直接查订单、改地址、发起退款**——因为「查订单」和「问政策」其实是一件事的两半，只答不做的机器人，用户还得再找人工。

> [!IMPORTANT]
> **这个案例的分水岭**
>
> **从「只读」跨到「写」的那一刻，项目性质就变了。**
> 只读系统的错误是「答错」，可以道歉；写系统的错误是「钱少了」，要赔。所以这个案例的全部难点都在**护栏**上，不在模型上。

---

## 29.2 需求澄清：把「能退款」拆成四条规则

| 轮次 | 客户说 | 你追问 | 澄清结果 |
| --- | --- | --- | --- |
| 1 | 「机器人直接给用户退款」 | 「退错了谁承担？」 | 客户沉默 → 达成共识：**必须设金额上限** |
| 2 | 「上限设 5000 元吧」 | 「近 30 天平均客单价多少？」 | 187 元 → 上限改为 **200 元**（约等于 P75 客单价） |
| 3 | 「用户说退款就退」 | 「怎么防止重复提交？」 | 需**幂等键** + 会话状态锁 |
| 4 | 「改地址也要能做」 | 「改完发现是诈骗怎么办？」 | 改地址**可回滚**（30 分钟内可撤销），且记录原值 |

四条规则最终写成：

```text
① 退款 ≤200 元：Agent 可直接执行，事后抽检
② 退款 200–2000 元：Agent 起草，人工一键确认
③ 退款 >2000 元 或 涉及投诉：直接转人工，Agent 不介入
④ 改地址：可直接执行，保留原值，30 分钟内可撤销；单日单用户上限 2 次
```

> [!TIP]
> **「200 元」这个数字怎么来的**
>
> 不是拍的。取近 30 天客单价的 P75 作为上限，理由是：**P75 以下的退款即使全错，损失也在可承受范围（日均 6 万咨询 × 退款占比 3% × 200 元 × 错误率 0.03% ≈ 每日 108 元）**。
> 报价和护栏设计里，**所有阈值都应该有算式支撑**，这是让客户放心签字的关键。

## 29.3 约束清单

| 约束 | 具体 | 影响 |
| --- | --- | --- |
| 峰值 | 大促 QPS 是平日 3 倍 | 弹性扩容 + 排队 + 降级链 |
| 风险 | 退款、改地址是写操作 | 限额 + 幂等 + 人审 + 可回滚 |
| 成本 | 单次咨询成本要低于人工（3.5 元） | 模型分级 + 语义缓存 + 小模型分类 |
| 体验 | 用户不愿等 | 流式输出 + 首响 <2 s |
| 准确 | 错退款直接损失钱 | 金额阈值 + 双重校验（工具侧 + 业务侧） |
| 合规 | 不得承诺平台无法履约的事 | 话术白名单 + 禁用词过滤 |

## 29.4 被否决的四个方案

| 方案 | 看起来的优点 | 否决理由 |
| --- | --- | --- |
| A 纯 RAG 问答（不做写操作） | 风险最低、两周上线 | 客户核心痛点是「用户还得再找人工」，**解决率上不去** |
| B 全开放写权限 | 体验最好 | 测试期出现重复退款，**一次事故就够终止项目** |
| C 全部转人工确认 | 零风险 | 人工成本没降，客户不接受 |
| D 用大模型做意图分类 | 省一个模型 | 6 万次/日 × 分类调用，**成本翻倍**，且小模型分类准确率已够（94%） |

> [!WARNING]
> **方案 B 是真实发生过的**
>
> 测试期一个用户连发三次「退款」，Agent 执行了三次退款。虽然金额不大，但**这类事故的性质是「系统会重复扣钱」**，一旦被发到社交媒体，项目基本结束。
> 从那以后我们的规矩是：**任何写操作，第一天就要有幂等键。**

## 29.5 总体架构

| 层 | 设计 | 关键参数 |
| --- | --- | --- |
| 编排 | Router 分流（售前/售后/物流/投诉）→ 售后走 ReAct Agent，其余走 RAG | 分类准确率 94%，误判可被用户纠正 |
| 工具（只读） | query_order、query_logistics、query_policy、query_inventory | 超时 2 s，失败重试 1 次 |
| 工具（写） | update_address、refund、create_ticket | 幂等键必填，返回结构化错误码 |
| 护栏 | 金额阈值分级、每日退款次数上限（3 次/用户）、幂等、审计 | 见 29.2 四条规则 |
| 检索 | 政策类走 RAG（混合检索 + 重排），答案带政策条款号 | 政策禁止凭记忆回答 |
| 成本 | 意图分类用小模型；问答用中模型；复杂投诉转人工；高频问题语义缓存 | 缓存命中 28% |
| 降级 | 模型超时 → 模板应答 + 转人工；向量库异常 → 纯 FAQ 命中 | 降级要告知用户 |
| 观测 | 每次工具调用记录 trace_id、参数、返回码、耗时 | 见 16.7 |

## 29.6 工具设计：这个案例最值得学的部分

写操作工具和只读工具的设计原则完全不同。对照表：

| 设计项 | 只读工具 | 写工具 |
| --- | --- | --- |
| 幂等 | 不要求 | **必须**（幂等键 = 会话 ID + 操作类型 + 业务单号） |
| 参数校验 | 宽松 | 严格（金额、地址格式、订单状态） |
| 返回值 | 数据 | 数据 + **操作结果 + 可撤销凭据** |
| 错误码 | 简单 | 细分（见下表） |
| 权限 | 只读账号 | 最小权限账号 + 业务侧二次校验 |
| 审计 | 记录调用 | 记录调用 + **变更前后值** |

**写工具的错误码设计（这个细节最能体现专业度）**：

| 错误码 | 含义 | Agent 应对 |
| --- | --- | --- |
| `ORDER_NOT_FOUND` | 订单不存在 | 请用户核对订单号，不猜 |
| `ORDER_STATUS_INVALID` | 当前状态不允许该操作 | 解释原因 + 给出可行路径 |
| `AMOUNT_EXCEED_LIMIT` | 超限额 | 转人工，不尝试拆分 |
| `DUPLICATE_REQUEST` | 幂等键重复 | 告知「已处理」，不重试 |
| `PERMISSION_DENIED` | 无权限 | 转人工，不解释细节 |
| `UPSTREAM_TIMEOUT` | 上游超时 | 重试 1 次，仍失败则转人工 |

> [!IMPORTANT]
> **为什么错误码要细分**
>
> 如果所有失败都返回「操作失败」，Agent 只会做一件事——**重试**。而重试在写操作里是最危险的动作。
> 细分错误码的本质是**告诉模型「这种情况该怎么办」**，把「模型猜」变成「按规则走」。

## 29.7 关键调优：四个真实问题

| 问题 | 现象 | 解法 | 效果 |
| --- | --- | --- | --- |
| 工具乱选 | 用户问政策，模型去查订单 | 工具描述补「何时使用 / 何时不要用」；Router 先分类 | 工具正确率 78% → 94% |
| 重复退款 | 用户重复说「退款」触发两次 | 幂等键 + 会话状态标记 | 重复操作 0 |
| 幻觉政策 | 编造「7 天无理由」的具体条件 | 政策必须走 RAG，禁止模型凭记忆回答 | 政策类幻觉率 6% → 0.4% |
| 大促超时 | P95 从 2.5 s 涨到 9 s | 扩容 + 缓存 + 降级到小模型 + 排队提示 | 大促 P95 回到 4.1 s |

**语义缓存的做法**（成本优化的关键）：

```text
用户问题 → Embedding → 在缓存库中找相似度 >0.95 的历史问题
  ├─ 命中且答案未过期 → 直接返回（成本≈0）
  └─ 未命中 → 正常链路，答案写入缓存（TTL 24h，政策类 TTL 1h）
```

> [!TIP]
> **语义缓存的阈值不要设太低**
>
> 0.90 会导致「退货」和「换货」被当成同一个问题，答案串了。**0.95 是经验起点**，且政策类内容必须设短 TTL（政策会变）。

## 29.8 上线：只读 → 低风险写 → 高风险写

| 阶段 | 时间 | 开放能力 | 门槛 |
| --- | --- | --- | --- |
| 一 只读 | 第 1–4 周 | 查订单、查物流、政策问答 | 自动解决率 ≥45% |
| 二 低风险写 | 第 5–8 周 | 改地址（可回滚）、创建工单 | 误操作率 ≤0.1%，且全部可回滚 |
| 三 限额退款 | 第 9–12 周 | ≤200 元退款 | 误操作率 ≤0.05%，人工抽检 200 笔 |
| 四 大促压测 | 第 13–14 周 | 全量 + 3 倍流量 | P95 ≤5 s，降级链验证通过 |

> [!IMPORTANT]
> **这个顺序不能颠倒**
>
> 我们见过太多项目「一步到位」，结果第一个月就在处理事故，没有时间优化效果。
> **每上一个台阶，都要有一个可量化的门槛**，达不到就停在原地优化——这不是保守，这是让项目活下来。

## 29.9 指标结果

| 指标 | 数值 | 测量方法 |
| --- | --- | --- |
| 自动解决率（整体） | 52% | 未转人工且 24h 内无重复咨询 |
| 自动解决率（售前） | 71% | 同上，按意图分组 |
| 自动解决率（售后） | 38% | 同上（售后本身复杂） |
| 平均首响 | 1.4 s | 生产监控 P50 |
| 单次咨询成本 | 3.5 元 → 0.4 元 | 总成本 / 咨询量 |
| 误操作率 | 0.03% | 全部为低金额改地址，均可回滚 |
| 大促 P95 | 4.1 s | 峰值期间监控 |
| 用户满意度（售后） | 82% → 86% | 会话结束评价 |

> [!WARNING]
> **「自动解决率 52%」要拆开讲**
>
> 整体 52% 听起来一般，但拆开是「售前 71% / 售后 38%」。
> **只报整体数字会被质疑，拆开讲反而显得真实**——因为所有人都知道售后难。这也是方案写作的一个技巧：主动暴露结构性差异，比给一个漂亮平均数更可信。

## 29.10 成本与商务

| 项 | 金额 | 说明 |
| --- | --- | --- |
| 实施人力 | 10 人月 × 3.2 万 = 32 万 | 含工具开发、护栏、压测 |
| 数据工程 | 2 人月 × 2.6 万 = 5.2 万 | 政策库 + 历史工单挖掘 |
| 模型调用（年） | 60 万 | 含大促峰值；语义缓存已省 28% |
| 基础设施 | 8 万/年 | 云资源 |
| 首年运维 | 12 万 | 含话术迭代 |
| 成本小计（首年） | 117.2 万 | |
| 报价（毛利 30%） | **167 万（首年）** | 次年起 78 万/年（模型 + 运维） |

**客户侧收益**：按 52% 自动解决、日均 6 万次计算，每日节省人工约 3.1 万次 × 3.5 元 ≈ 10.9 万元，年化约 3900 万元（大促另计）。**这个数字大得离谱，所以要主动打折**——方案里写「按 30% 保守估算，年化节省约 2300 万元」，反而更容易被接受。

## 29.11 踩过的四个坑

| # | 坑 | 后果 | 改法 |
| --- | --- | --- | --- |
| 1 | 一开始放开写权限 | 测试期重复退款 | 限额 + 幂等 + 人审，三件套同时上 |
| 2 | 没有意图路由 | 模型在「查订单」和「问政策」间摇摆 | 加 Router，工具正确率 +16 pt |
| 3 | 缓存没做语义去重 | 「怎么退货」「退货怎么弄」重复计费 | 语义缓存，命中 28% |
| 4 | 降级时静默降质 | 用户以为系统坏了，投诉增加 | 降级必须提示「当前为简化模式」 |

---

## 29.12 如果重来，会怎么改

| 改动 | 理由 |
| --- | --- |
| 第一天就写幂等键 | 后补要改所有写工具，且历史数据无法追溯 |
| 错误码从一开始就细分 | 错误码是 Agent 的「行为指南」，后补等于重写工具层 |
| 把「话术白名单」前置到提示词之前 | 生成后再过滤，成本更高且会破坏语义 |
| 大促前做一次真实 3 倍流量压测 | 生产环境第一次遇到峰值就是事故 |

## 29.13 可复用的判断

> [!IMPORTANT]
> **三条可以带走**
>
> ① **写操作 = 风险敞口。** 上线顺序永远是：只读 → 低风险写（可回滚）→ 高风险写（人审）。一步到位是事故的开始。
> ② **所有阈值都要有算式。** 「200 元上限」背后是客单价 P75 与可承受损失的乘积。
> ③ **错误码是给模型看的说明书**，不是给运维看的日志。细分错误码 = 减少模型瞎猜。

## 29.14 本章考点速记

<details>
<summary><b>折叠背诵版</b></summary>

> **约束五条**：峰值 3 倍、写操作风险、成本要低于人工、首响 <2 s、错退款直接损失钱。
>
> **四个否决**：纯问答（解决率低）、全开放写（重复退款）、全转人工（成本没降）、大模型做分类（成本翻倍）。
>
> **写工具六要素**：幂等键、严格参数校验、返回可撤销凭据、细分错误码、最小权限、变更前后值审计。
> **错误码六类**：订单不存在 / 状态不允许 / 超限额 / 重复请求 / 无权限 / 上游超时。
>
> **上线四阶段**：只读 → 低风险写（可回滚）→ 限额退款 → 大促压测，每阶段有量化门槛。
>
> **指标**：整体解决率 52%（售前 71% / 售后 38%）、首响 1.4 s、成本 3.5→0.4 元、误操作 0.03%、大促 P95 4.1 s。
>
> **一句话**：写操作的风险不在模型，在护栏。

</details>
