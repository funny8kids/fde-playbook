## 这一篇解决什么问题

RAG 让模型「会查」，Agent 让模型「会做」。一旦它能动手，问题就从「答得准不准」变成「**会不会闯祸**」。所以这一篇的主线不是「怎么让它更强」，而是：

```text
能做什么   → 工具契约与集成（14）
怎么组织   → 编排拓扑与状态机（13、16）
怎么证明对 → 评测四维 + 轨迹（15）
怎么不出事 → 护栏五层 + 沙箱 + 红队（15）
```

> [!important] 一句话
> **Agent 项目的全部难点都在护栏上，不在模型上。** 写操作的风险不是「模型可能说错」，是「模型可能做错，而且做错了要赔钱」。

## 为什么是这个顺序

**先看边界（13）→ 再给手段（14）→ 再管风险（15）→ 最后才谈多角色（16）。**

第 16 章放在最后是有意的：**多智能体是最容易被滥用的东西**。如果先读 16，你会觉得「什么都该拆成多个角色」；读完 13–15 再读 16，你才会问那句正确的话——「这个职责真的需要隔离吗？」

> [!warning] 一个真实的教训
> 我们见过一个项目，4 个角色互相评审一份合同，跑得挺好，但成本是单 Agent 的 3.4 倍、延迟 2–3 倍。
> 复盘时发现：**其中 2 个角色的输出从未改变最终结论**。删掉它们，成本降 40%，效果不变。

## 本篇三条核心判断

> [!success]- 展开看
> ① **写操作 = 风险敞口，上线顺序永远是：只读 → 低风险写（可回滚）→ 高风险写（人审）。** 一步到位是事故的开始（13.7、15.5、29.8）。
>
> ② **工具返回的内容是「数据」，不是「指令」。** 间接注入是 Agent 时代最被低估的攻击面——攻击者不需要接触你的系统，只要在你能检索到的文档里写一句话（15.8）。
>
> ③ **状态以工具返回为准，不以模型声称的为准。** 模型说「已退款」不算数，工具返回 `success` 才算数（13.12）。
